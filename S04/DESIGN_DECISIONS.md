### D-01. Посылка загружается только в пределах доступа пользователя

**Контекст:** почти все точки входа принимают id посылки от клиента (`/parcels/{id}`,
`/issue`, `/return`, `/cancel`, `PUT`). Если сервер сначала найдёт посылку по id, а потом
проверит только роль, оператор любого пункта сможет выдать чужую посылку (T-02), а
покупатель — прочитать чужую (T-01). Проверку «посылка моя?» легко забыть в одной из
десятка операций.

**Решение:**

- Пользователь определяется только по токену: из него берётся `userId`, роль и привязка
  (магазин продавца или пункт оператора) загружаются из базы на каждом запросе.
- Все чтения и изменения посылки идут через один метод `ParcelAccess.VisibleTo(user)`,
  который добавляет условие доступа прямо в запрос к базе:
  - покупатель — `recipient_id = user.Id`;
  - продавец — `store_id = user.StoreId`;
  - оператор — `pickup_point_id = user.PickupPointId`.
- Тот же фильтр применяется к спискам `GET /parcels`.
- Если посылка не найдена с этим условием, ответ 404 — одинаковый для «нет такой» и
  «чужая».
- Только после этого проверяется роль для конкретной операции (атрибут роли на каждой
  точке входа, по умолчанию доступ запрещён).

**Обоснование:** условие доступа стоит в самом запросе к базе, поэтому чужая посылка
вообще не попадает в обработчик — забыть проверку в новой операции нельзя, если операция
получает посылку через `ParcelAccess`. Карточка, история, списки и изменения проверяются
одним и тем же правилом. 404 вместо 403 не даёт перебором узнать, какие id существуют.
Привязки читаются из базы, а не из токена, чтобы смена пункта у оператора действовала
сразу, а не после истечения токена.

**Связанные угрозы:** T-01, T-02, T-03

**Связанные требования:** SR-01, SR-02, SR-10

**Будущая проверка** (дополняет критерии SR-01, SR-02, SR-10):

1. **Условие:** покупатели A и B, у A посылка P1. **Действие:** B запрашивает
   `GET /parcels/P1` и `GET /parcels/P1/history`, затем `GET /parcels/<несуществующий id>`.
   **Ожидаемый результат:** все три ответа 404 с одинаковым телом.
2. **Условие:** в базе посылки двух магазинов и двух пунктов. **Действие:** каждый тестовый
   пользователь запрашивает `GET /parcels`. **Ожидаемый результат:** в списке только
   посылки по его привязке.
3. **Условие:** P1 в статусе «Ожидает в пункте выдачи» в пункте 1. **Действие:** оператор
   пункта 2 вызывает `/issue` и `/return` для P1. **Ожидаемый результат:** 404, статус и
   число записей истории P1 не изменились. Оператор пункта 1 тот же вызов выполняет успешно.
4. **Условие:** оператор O переведён из пункта 1 в пункт 2, токен выдан до перевода.
   **Действие:** O со старым токеном запрашивает посылку пункта 1. **Ожидаемый
   результат:** 404 — привязка взята из базы, а не из токена.

**Что уже есть в EK1:** `ParcelAccess.VisibleTo` используется в `GET /parcels`,
`GET /parcels/{id}` и `GET /parcels/{id}/history`. Проверки 1 и 2 написаны как тесты
`ParcelAccessTests` на PostgreSQL в Docker. Проверка 3 появится вместе с `/issue` и
`/return`, проверка 4 — вместе с изменением привязок.

**Ограничения и последствия:** лишний запрос к базе за привязкой на каждый запрос — для
учебной нагрузки несущественно. Защита держится на правиле «посылку получать только через
`ParcelAccess`»: прямой запрос к таблице посылок в обход него снова откроет T-01/T-02,
поэтому проверки 1–3 нужно прогонять для каждой новой точки входа. Фоновая задача работает
от имени сервиса и `ParcelAccess` не использует.

### D-02. Отдельные модели запросов и ответов, серверные поля задаёт только сервер

**Контекст:** если в `PUT /parcels/{id}` или `/arrive` принимать объект посылки целиком,
клиент может дописать в JSON поля, которых нет в его операции: `status`, `storeId`,
`recipientId` после отправки, `storageDeadline`, `changedBy` (T-04, T-05). Одним запросом
обходятся сразу SR-03…SR-07. Обратная сторона — если отдавать объект целиком, оператор
получит стоимость вещей (T-09).

**Решение:**

- Для каждой операции своя модель запроса только с разрешёнными полями, например
  `ArriveRequest { StorageCell }`, `ReturnRequest { Reason, Comment }`,
  `UpdateParcelRequest { RecipientId, PickupPointId, Items }`.
- Неизвестные поля в JSON — ошибка 400 (в System.Text.Json:
  `UnmappedMemberHandling = Disallow`), а не молчаливое игнорирование.
- Сущность `Parcel` из запроса никогда не заполняется. У неё нет публичных сеттеров для
  `Status`, `StoreId`, `StorageDeadline`; статус меняется только методами `Ship()`,
  `Arrive()`, `Issue()`, `Return()`, `Cancel()`, `ConfirmReturned()`.
- Сервер сам задаёт: `StoreId` — из привязки продавца, автора записи истории — из токена
  (или «сервис» для фоновой задачи), `StorageDeadline` — время прибытия по часам сервера
  (UTC) + 7 дней.
- `Update()` разрешён только в статусе «Создано», иначе 409 (SR-05).
- Получатель проверяется: существует и имеет роль «Покупатель», пункт выдачи существует.
- Ответы тоже собираются по ролям: `OperatorParcelView` без стоимости и без кода получения.
- Ограничения размера: в посылке не больше 50 позиций, строки ограничены по длине.

**Обоснование:** белый список полей на каждую операцию проще проверить, чем помнить, какие
поля сущности нельзя менять. Отказ на лишние поля, а не их пропуск, делает попытку видимой
и упрощает тест: результат один и тот же — 400, состояние не изменилось. Закрытые сеттеры
переносят правило в модель: даже ошибка в контроллере не сможет напрямую выставить статус.

**Связанные угрозы:** T-04, T-05, T-09, частично T-10

**Связанные требования:** SR-04, SR-05, SR-06, SR-07, SR-08

**Будущая проверка** (дополняет критерии SR-04, SR-05, SR-06, SR-08):

1. **Условие:** посылка в статусе «Создано» магазина 1. **Действие:** продавец отправляет
   `PUT` с допустимыми полями и дополнительно `"status": "Выдано"`, `"storeId": 2`.
   **Ожидаемый результат:** 400, посылка совпадает с состоянием до запроса.
2. **Условие:** посылка в статусе «Передано в доставку». **Действие:** оператор вызывает
   `/arrive` с `"storageCell": "A-12", "storageDeadline": "<через 30 дней>"`.
   **Ожидаемый результат:** 400; тот же запрос без `storageDeadline` — успешно, срок равен
   времени прибытия + 7 дней.
3. **Условие:** посылка в статусе «Передано в доставку». **Действие:** продавец своего
   магазина отправляет `PUT` с новым пунктом выдачи. **Ожидаемый результат:** 409, пункт
   прежний.
4. **Условие:** посылка пункта оператора. **Действие:** оператор запрашивает карточку и
   список. **Ожидаемый результат:** в JSON нет полей стоимости и кода получения.

**Что уже есть в EK1:** `UnmappedMemberHandling.Disallow` включён для всех запросов,
у `Parcel` закрытые сеттеры, статус меняется только методами (`Ship`, `Arrive` — пока
используются тестовыми данными). Тесты проверяют 400 на лишнее поле в `POST /auth/login`
и отсутствие стоимости в карточке для оператора (часть проверки 4; кода получения ещё нет).
Проверки 1–3 появятся вместе с `PUT /parcels/{id}` и `/arrive`.

**Ограничения и последствия:** на каждую операцию нужна своя модель — больше классов и
маппинга. Внешние клиенты, которые шлют лишние поля, будут получать 400; в проекте таких
клиентов нет. Защита от лишних полей не заменяет D-01: допустимое поле с чужим id всё
равно проверяется через `ParcelAccess`.

### D-03. Переход статуса — одно условное обновление вместе с записью истории

**Контекст:** исходное предположение на S02 было таким: SR-03 выполняется, если перед
сменой статуса проверить текущий. На S03 нашёлся контрпример (T-06): оператор отмечает
«Выдано» в ту же секунду, когда фоновая задача оформляет возврат просроченной посылки.
Оба читают статус «Ожидает в пункте выдачи», оба проверку проходят, оба записывают — посылка
и выдана, и возвращается, в истории два перехода из одного статуса. Та же щель позволяет
выдать просроченную посылку до запуска фоновой задачи (T-05). По итогам SR-03 дополнен
критерием для одновременных запросов, а здесь выбран механизм.

**Решение:**

- Каждый переход выполняется в одной транзакции базы данных из двух действий:
  1. `UPDATE parcels SET status = @new, ... WHERE id = @id AND status = @expected`
     (для выдачи дополнительно `AND storage_deadline > now()`);
  2. если обновлена ровно одна строка — `INSERT` записи в `parcel_status_history`
     (автор, время UTC, из какого статуса, в какой, причина).
- Если обновлено 0 строк — транзакция откатывается, ответ 409, история не меняется.
- Фоновая задача использует тот же метод перехода с автором «сервис».
- Пользователю базы, под которым работает приложение, выданы на таблицу истории только
  `SELECT` и `INSERT`; точек входа для изменения истории в API нет.

**Обоснование:** проверка статуса и запись происходят в одном операторе `UPDATE`, поэтому
между ними нельзя вклиниться: из двух одновременных переходов база применит только тот,
который первым изменит строку, второй увидит уже новый статус и получит 0 строк. Проверка
срока в том же условии закрывает окно между истечением срока и запуском задачи. Переход и
запись истории в одной транзакции — нельзя получить смену статуса без записи или запись
без смены. Рассматривал блокировку строки (`SELECT ... FOR UPDATE`) — даёт ту же гарантию,
но держит блокировку дольше и требует аккуратности с порядком действий; условное
обновление проще и не зависит от уровня изоляции.

**Связанные угрозы:** T-04, T-05, T-06, T-07 (история выдачи)

**Связанные требования:** SR-03, SR-06, SR-07

**Будущая проверка** (дополняет критерии SR-03, SR-06, SR-07):

1. **Условие:** посылка в статусе «Ожидает в пункте выдачи», срок истекает через
   1 секунду. **Действие:** после истечения срока параллельно запускаются `/issue` с верным
   кодом и метод фоновой задачи, 50 повторов на отдельной тестовой базе PostgreSQL.
   **Ожидаемый результат:** в каждом повторе итоговый статус «Возврат», `/issue`
   получил 409, в истории ровно одна запись о переходе из «Ожидает в пункте выдачи».
2. **Условие:** то же, но срок не истёк. **Действие:** параллельно два `/issue` от
   оператора. **Ожидаемый результат:** один 200, один 409, одна запись в истории.
3. **Условие:** тестовая ошибка при вставке записи истории. **Действие:** вызвать
   переход. **Ожидаемый результат:** статус посылки не изменился.
4. **Условие:** подключение к базе под пользователем приложения. **Действие:**
   `UPDATE` и `DELETE` на `parcel_status_history`. **Ожидаемый результат:** отказ
   в доступе от PostgreSQL.

**Ограничения и последствия:** второй из одновременных запросов всегда получает 409 —
клиенту нужно перечитать посылку. Проверка 1 имеет смысл только на настоящем PostgreSQL,
не на базе в памяти. Неизменность истории опирается на права пользователя базы:
администратор базы её изменить может — это допущение модели (база доступна только серверу).

### D-04. Выдача по одноразовому коду, который видит только получатель

**Контекст:** граница TB-2 — сервис не видит пункт выдачи и знает о выдаче только со слов
оператора. Оператор может отметить «Выдано», не отдав посылку (T-07), и покупатель ничего
не докажет. SR-11 требует подтверждения, которого нет у оператора.

**Решение:**

- При отметке прибытия сервер генерирует случайный 6-значный код
  (`RandomNumberGenerator`), сохраняет только его хеш и обнуляет счётчик неверных попыток.
- Код показывается в карточке посылки только покупателю-получателю и только в статусе
  «Ожидает в пункте выдачи». В моделях ответа оператору и продавцу поля кода нет (D-02).
- `/issue` принимает код; сервер сравнивает хеши. При неверном коде счётчик растёт, после
  5 неверных попыток выдача по посылке блокируется, остаётся только возврат.
- Сама смена статуса на «Выдано» выполняется по D-03, при неверном коде перехода нет.
- После выдачи код становится недействительным.

**Обоснование и сравнение вариантов:**

Рассматривал два способа подтвердить, что посылку забрал получатель.

| | А. Покупатель подтверждает получение в своём аккаунте | Б. Код у покупателя, оператор вводит его при выдаче (выбран) |
| --- | --- | --- |
| Кто подтверждает | Покупатель после выдачи | Покупатель показывает код до выдачи |
| Если оператор не отдал посылку | Покупатель не подтверждает — но статус «Выдано» уже стоит или посылка висит | Выдать без кода нельзя |
| Если покупатель недобросовестный | Забрал и не подтвердил — «я не получал», доказать выдачу нечем | Код показан у стойки — выдача подтверждена |
| Нагрузка на покупателя | Действие в приложении после выдачи | Показать код с телефона |
| Роль покупателя | Нужно менять: появляется изменяющее действие | Остаётся только просмотр |

Главный компромисс: вариант А защищает от недобросовестного оператора только после
события и оставляет спор, когда покупатель отказывается подтверждать; вариант Б
подтверждает выдачу в момент передачи, но переносит риск на секретность кода. Выбран Б:
он закрывает и ложное «Выдано» от оператора, и ложное «не получал» от покупателя.

**Допущения и границы применимости:** у покупателя есть доступ к своему аккаунту в момент
получения; код не передаётся третьим лицам. Если покупатель сам продиктует код мошеннику
«из доставки», вариант Б не защищает — это вне границы сервиса. Подбор кода ограничен:
5 попыток из 1 000 000 вариантов — вероятность угадать 0,0005%.

**Когда пересмотреть выбор:** если появятся случаи выдачи по выманенному коду или многим
покупателям будет неудобно показывать код — добавить проверку документа с записью его
последних цифр или двухэтапный вариант (код + подтверждение покупателем).

**Связанные угрозы:** T-07

**Связанные требования:** SR-11, SR-07, SR-01

**Будущая проверка** (дополняет критерий SR-11, учитывает ограничение по подбору):

1. **Условие:** посылка в статусе «Ожидает в пункте выдачи». **Действие:** оператор
   вызывает `/issue` без кода и с неверным кодом. **Ожидаемый результат:** отказ (403),
   статус прежний, в истории нет записи о выдаче.
2. **Условие:** то же. **Действие:** 5 неверных кодов, затем верный. **Ожидаемый
   результат:** шестая попытка с верным кодом отклонена, статус «Ожидает в пункте выдачи».
3. **Условие:** посылка ожидает выдачи. **Действие:** запросить карточку от покупателя-
   получателя, оператора пункта, продавца магазина. **Ожидаемый результат:** код есть
   только в ответе покупателю; в базе код хранится не в открытом виде.
4. **Условие:** посылка выдана по коду. **Действие:** повторный `/issue` с тем же кодом.
   **Ожидаемый результат:** 409, одна запись о выдаче в истории.

**Ограничения и последствия:** при 5 неверных попытках добросовестный получатель тоже
не сможет забрать посылку — она уйдёт в возврат. Появляется новый значимый объект — код
получения; его раскрытие равно возможности забрать посылку. Паспорт обновлён: покупатель
видит код, выдача без кода невозможна.

## Оставшиеся разрывы и доработка к EK1

- **T-08 → SR-09:** решение не записано. В EK1 уже есть одинаковый ответ на неверный
  логин и неверный пароль и хеширование паролей через `PasswordHasher` из ASP.NET Core
