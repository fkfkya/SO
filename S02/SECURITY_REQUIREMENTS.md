## Подробно

### SR-01. Доступ только к своим посылкам

- **Требование:** сервис показывает посылку и её историю только связанным с ней пользователям:
  покупателю, если он получатель; продавцу, если посылка его магазина; оператору, если
  посылка адресована его пункту выдачи. То же правило действует для списков.
- **Почему это безопасность:** в посылке есть имя и телефон получателя, состав и стоимость
  заказа, пункт выдачи. Если перебирать id и получать чужие посылки, утекают персональные
  данные и видно, где лежат дорогие заказы.
- **Критерий приёмки:**
  - покупатель B запрашивает посылку покупателя A по id — ответ такой же, как на
    несуществующий id (404), данных посылки в ответе нет;
  - продавец магазина 2 и оператор пункта 2 так же не получают посылку магазина 1 для пункта 1;
  - в списке посылок каждого пользователя только посылки, разрешённые по правилу выше;
  - покупатель A свою посылку и её историю получает.
- **ASVS:** `v5.0.0-8.2.2` — доступ к конкретным объектам только с явным разрешением (IDOR/BOLA).
  Пункт применим напрямую: доступ к посылке зависит не от роли, а от связи пользователя
  с конкретной посылкой. По нему уточнён критерий: отказ не должен отличаться от ответа
  «не найдено», иначе перебором id можно узнать, какие посылки существуют, а проверять
  нужно не только карточку, но и списки.
- **Связанные T / D:** T-01 / D-01, D-04

### SR-02. Действия только для своей роли

- **Требование:** каждое действие с посылкой разрешено только определённой роли:

  | Действие | Кто может |
  | --- | --- |
  | Создать, изменить, отменить посылку; «Передано в доставку»; «Возвращено продавцу» | Продавец |
  | Отметить прибытие и место хранения; «Выдано»; оформить возврат | Оператор |
  | Только просмотр | Покупатель |

- **Почему это безопасность:** если покупатель сможет сам поставить «Выдано» или «Возврат»,
  а продавец — отметить выдачу, статус перестанет отражать то, что произошло на самом деле.
  Ложное «Выдано» скрывает пропавшую посылку, ложный возврат — заставляет магазин ждать
  посылку, которой нет.
- **Критерий приёмки:**
  - покупатель вызывает отметку о выдаче своей посылки напрямую через API — отказ (403),
    статус и история не изменились;
  - продавец вызывает «Выдано» для посылки своего магазина — отказ, статус не изменился;
  - оператор пытается создать или отменить посылку — отказ, посылка не создана и не отменена;
  - оператор своего пункта отмечает выдачу ожидающей посылки — успешно.
- **ASVS:** `v5.0.0-8.2.1`.
- **Связанные T / D:** T-02, T-03 / D-01

### SR-03. Только допустимые переходы статусов

- **Требование:** статус меняется только по схеме из паспорта:
  «Создано» → «Передано в доставку» → «Ожидает в пункте выдачи» → «Выдано» или «Возврат»
  → «Возвращено продавцу»; «Создано» → «Отменено». Финальные статусы «Выдано»,
  «Возвращено продавцу» и «Отменено» больше не меняются.
- **Почему это безопасность:** перескок статуса позволяет, например, отметить выдачу
  посылки, которая не приходила в пункт, или превратить выданную посылку в возврат и
  получить и вещи, и «возврат» в учёте магазина.
- **Критерий приёмки:**
  - отметка «Выдано» для посылки в статусе «Передано в доставку» — отказ (409), статус прежний;
  - оформление возврата для посылки в статусе «Выдано» — отказ, статус прежний, заявка
    на возврат не создана;
  - отмена посылки в статусе «Передано в доставку» — отказ;
  - при любом отказе в истории не появляется новая запись о переходе;
  - отметка «Выдано» и автоматический возврат по одной посылке выполняются одновременно —
    успешен только один переход, итоговый статус либо «Выдано», либо «Возврат», в истории
    одна запись о переходе из «Ожидает в пункте выдачи».
- **ASVS:** `v5.0.0-2.3.1`, `v5.0.0-2.3.3`.
- **Связанные T / D:** T-04, T-06 / D-03

### SR-04. Привязки посылки определяет сервер

- **Требование:** при создании посылки магазин берётся из привязки продавца, а не из запроса.
  Получателем может быть только существующий пользователь с ролью «Покупатель», пунктом
  выдачи — только существующий пункт. Автор каждого действия в истории — вошедший
  пользователь (или сервис для автоматического возврата), а не значение из запроса.
- **Почему это безопасность:** если магазин или автора можно указать в запросе, продавец
  сможет создавать посылки от имени чужого магазина, а запись в истории можно будет
  приписать другому человеку. Посылка, оформленная на оператора или продавца как
  на «получателя», откроет её данные не тому пользователю.
- **Критерий приёмки:**
  - продавец магазина 1 передаёт в запросе магазин 2 — посылка создана для магазина 1
    либо запрос отклонён; в магазине 2 посылка не появилась;
  - получатель — несуществующий пользователь или пользователь с ролью «Оператор» —
    отказ (400), посылка не создана;
  - запрос смены статуса с полем «автор = другой пользователь» — в истории записан
    вошедший пользователь.
- **ASVS:** `v5.0.0-8.3.1`.
- **Связанные T / D:** T-04 / D-02

### SR-05. Посылку нельзя менять после отправки

- **Требование:** после статуса «Передано в доставку» состав посылки, стоимость, получатель
  и пункт выдачи не меняются никем.
- **Почему это безопасность:** состав — основа для спора «что было в посылке». Смена пункта
  или получателя после отправки позволяет перенаправить чужую посылку.
- **Критерий приёмки:**
  - продавец меняет состав или пункт выдачи посылки в статусе «Передано в доставку» —
    отказ, данные посылки совпадают с данными до запроса;
  - в статусе «Создано» продавец своего магазина меняет состав — успешно.
- **ASVS:** `v5.0.0-8.2.3` — права на поля зависят от статуса объекта.
- **Связанные T / D:** T-04 / D-02

### SR-06. Просроченную посылку нельзя выдать

- **Требование:** срок хранения сервер считает сам: время прибытия по часам сервера + 7 дней.
  Срок нельзя передать или продлить через запрос. После его окончания посылку нельзя выдать,
  даже если фоновая задача ещё не успела оформить возврат.
- **Почему это безопасность:** по просроченной посылке магазин уже ждёт возврат. Если оператор
  может выдать её позже или сдвинуть срок, посылка уходит человеку, а в учёте висит как
  возврат — появляется расхождение, которое можно использовать, чтобы скрыть пропажу.
- **Критерий приёмки:**
  - срок хранения истёк, возврат ещё не оформлен, оператор отмечает выдачу — отказ,
    статус «Ожидает в пункте выдачи» или «Возврат», но не «Выдано»;
  - оператор передаёт в запросе прибытия свой срок хранения — сохранённый срок равен
    времени прибытия + 7 дней;
  - после работы фоновой задачи у просроченной посылки статус «Возврат», причина
    «Истёк срок хранения», автор в истории — сервис.
- **ASVS:** —, это правило моего продукта.
- **Связанные T / D:** T-04, T-05 / D-02, D-03

### SR-07. Неизменяемая история статусов

- **Требование:** каждый успешный переход статуса сохраняется в истории: посылка, автор,
  время (UTC), прежний и новый статус, причина (для возврата). Записи истории нельзя изменить
  или удалить ни одной ролью.
- **Почему это безопасность:** при споре («посылку не выдавали», «возврат не оформлял»)
  история — единственный способ установить, кто и когда сделал действие. Если её можно
  править, она ничего не доказывает.
- **Критерий приёмки:**
  - после выдачи в истории есть запись с оператором, временем, переходом
    «Ожидает в пункте выдачи» → «Выдано»;
  - после возврата в записи есть причина;
  - запросы на изменение или удаление записи истории от любой роли отклоняются,
    количество и содержимое записей не меняются;
  - отклонённая попытка перехода не создаёт запись об успешном переходе.
- **ASVS:** `v5.0.0-16.2.1`, `v5.0.0-16.4.2`.
- **Связанные T / D:** T-04, T-06, T-07 / D-02, D-03, D-04

### SR-08. Оператор не видит стоимость

- **Требование:** в данных посылки, которые получает оператор пункта выдачи, нет стоимости
  вещей. Стоимость видят продавец своего магазина и покупатель-получатель.
- **Почему это безопасность:** оператору стоимость для работы не нужна, а знание, какие
  посылки дорогие, повышает риск кражи из пункта выдачи.
- **Критерий приёмки:**
  - оператор запрашивает карточку и список посылок своего пункта — поля стоимости в ответе нет;
  - продавец своего магазина в той же посылке стоимость видит.
- **ASVS:** `v5.0.0-8.2.3`.
- **Связанные T / D:** T-09 / D-02

### SR-09. Вход обязателен, подбор пароля ограничен

- **Требование:** все операции с посылками доступны только вошедшему пользователю. Без входа
  доступна только проверка работы сервиса. Подбор пароля ограничен: после 5 неудачных
  попыток подряд вход в аккаунт блокируется на 15 минут. Ответ на неудачный вход не
  сообщает, существует ли такой логин.
- **Почему это безопасность:** без входа или с подобранным паролем посторонний получает
  все права роли — у оператора, например, возможность отметить выдачу чужой посылки.
- **Критерий приёмки:**
  - запрос списка или карточки посылки без токена или с неверным токеном — 401,
    данных посылок нет;
  - 5 неверных паролей подряд для одного логина, затем верный — вход отклонён, пока
    не прошло 15 минут;
  - ответ на неверный пароль и на несуществующий логин одинаковый.
- **ASVS:** `v5.0.0-6.3.1`.
- **Связанные T / D:** T-08 / D пока нет (разрыв)

### SR-10. Изменения только в пределах своей привязки

- **Требование:** продавец изменяет только посылки своего магазина (правка, отмена,
  отправка, приём возврата), оператор — только посылки, адресованные его пункту выдачи
  (прибытие, выдача, возврат). Правильной роли для этого недостаточно.
- **Почему это безопасность:** SR-02 проверяет роль, SR-01 — только чтение. Без этого
  требования оператор любого пункта может отметить выдачу посылки, которая лежит в другом
  пункте, и скрыть её пропажу.
- **Критерий приёмки:**
  - оператор пункта 2 вызывает выдачу или возврат посылки пункта 1 — ответ такой же, как
    на несуществующую посылку (404), статус и история не изменились;
  - продавец магазина 2 отменяет или изменяет посылку магазина 1 — так же отказ, данные
    посылки прежние;
  - оператор пункта 1 выдаёт посылку своего пункта — успешно.
- **ASVS:** `v5.0.0-8.2.2`.
- **Связанные T / D:** T-02 / D-01

### SR-11. Выдача только с подтверждением получателя

- **Требование:** сервис принимает отметку «Выдано» только вместе с подтверждением,
  которое известно покупателю-получателю и не известно оператору и продавцу. Без верного
  подтверждения посылка остаётся в статусе «Ожидает в пункте выдачи». Число неверных
  попыток по одной посылке ограничено. Механизм подтверждения выбираю на S04.
- **Почему это безопасность:** сервис не видит пункт выдачи (граница TB-2 в модели угроз).
  Если выдача держится только на слове оператора, он может отметить «Выдано», не отдав
  посылку получателю, и покупатель не докажет, что её не получал.
- **Критерий приёмки:**
  - оператор отмечает выдачу без подтверждения или с неверным — отказ, статус
    «Ожидает в пункте выдачи», записи о выдаче в истории нет;
  - с верным подтверждением — статус «Выдано», в истории оператор и время;
  - подтверждение есть в ответах только покупателю-получателю, у оператора и продавца
    этого поля нет;
  - после 5 неверных попыток по посылке дальнейшие попытки выдачи отклоняются даже
    с верным подтверждением.
- **ASVS:** —, это правило моего продукта.
- **Связанные T / D:** T-07 / D-04

## Правила продукта без SR

Эти правила остаются в предметном описании; отдельного защитного свойства у них нет
или оно уже покрыто требованиями выше.

- Длина срока хранения — 7 дней. Само число — бизнес-правило; защитное свойство (срок
  нельзя обойти) описано в SR-06.
- Номер отслеживания уникален — нужно для учёта, не для защиты: доступ по номеру без
  входа запрещён (SR-01, SR-09).
- Причина возврата выбирается из списка — удобство учёта причин, а не защита.
- Фильтры, поиск и постраничный вывод списка — функциональность, на неё действует SR-01.

  нужно отдельное требование на управление привязками пользователей.
- Проверить, не стоит ли объединить SR-02 и SR-03 или SR-05 с SR-03.
- Значения 5 попыток и 15 минут в SR-09 — предварительные.
